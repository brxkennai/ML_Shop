# ML_Shop — Predicting Successful Purchases

**End-to-end Machine Learning project:** прогнозирование успешной покупки пользователя интернет-магазина на основе его предыдущей активности.

Проект охватывает полный цикл классического машинного обучения: генерацию данных, работу с PostgreSQL, построение признаков на SQL, обучение и оценку моделей, подбор гиперпараметров, пакетное получение предсказаний и автоматическое тестирование.

> **Disclaimer:** все данные синтетические. Проект создан в образовательных целях и не предназначен для использования в реальной коммерческой системе без дополнительной валидации.

## 1. Business Problem

**Задача:** определить вероятность того, что пользователь интернет-магазина совершит покупку со статусом `completed` в течение следующих 30 дней.

Для каждого пользователя в момент времени `T` используются данные о его активности за предыдущие 60 дней.

**Prediction target:**

- `target = 1` — в следующие 30 дней есть хотя бы один заказ, получивший итоговый статус `completed`;
- `target = 0` — таких заказов нет.

Признаки формируются исключительно на основе активности до момента `T`.

Такой подход может использоваться для приоритизации пользователей в маркетинговых кампаниях и CRM-сегментации.

## 3. Data

Используется синтетический набор данных, имитирующий деятельность интернет-магазина.

Основные сущности:

| Таблица | Содержание |
|---|---|
| `users` | Пользователи, даты регистрации, страна и дополнительные характеристики |
| `sessions` | Сессии пользователей и их продолжительность |
| `events` | Просмотры страниц, товаров, поиск, корзина и оформление заказа |
| `orders` | Заказы, даты, суммы и статусы |
| `payments` | Информация об оплатах |
| `support_tickets` | Обращения в поддержку |

Данные специально содержат пропущенные значения и разные статусы заказов (`completed`, `cancelled`, `refunded`, `pending`).

**Итоговый ML-датасет:**

- 2 500 пользователей;
- 8 временных срезов;
- 20 000 наблюдений;
- 10 входных признаков;
- бинарная целевая переменная `target`.

Один пользователь может присутствовать в нескольких временных срезах, поэтому случайное разбиение строк не используется.

## 4. Feature Engineering

Признаки рассчитываются в PostgreSQL с помощью SQL-запроса `sql/build_features.sql`.

Для каждого `snapshot_date = T` используется историческое окно:

```text
[T - 60 days, T)
```

Целевое окно:

```text
[T, T + 30 days)
```

Правая граница каждого интервала не включается.

### Используемые признаки

| Признак | Описание |
|---|---|
| `country` | Страна пользователя |
| `orders_last_60d` | Количество оформленных заказов за 60 дней |
| `sessions_last_60d` | Количество пользовательских сессий |
| `avg_session_duration_60d` | Средняя длительность сессий, завершённых к моменту прогноза |
| `events_last_60d` | Общее число событий |
| `page_views_60d` | Количество просмотров страниц |
| `product_views_60d` | Количество просмотров товаров |
| `searches_60d` | Количество поисковых событий |
| `cart_additions_60d` | Количество добавлений в корзину |
| `checkouts_60d` | Количество событий оформления заказа |

`sessions_last_60d` учитывает сессии, начатые в историческом окне. Для `avg_session_duration_60d` дополнительно требуется, чтобы `started_at + duration_seconds` было не позже момента прогноза: итоговая длительность ещё незавершённой сессии неизвестна. Если завершённых сессий в окне нет, средняя длительность остаётся пропуском.

### Target Definition

Целевая переменная определяется по заказам, созданным в течение 30 дней после момента прогноза и имеющим итоговый статус `completed`.

```sql
CASE
    WHEN COUNT(o.order_id) FILTER (
        WHERE o.created_at >= p.snapshot_date
          AND o.status = 'completed'
    ) > 0 THEN 1
    ELSE 0
END AS target
```

Верхняя граница целевого окна задаётся условием соединения с таблицей `orders`.

**Ограничение:** статус `completed` рассматривается как итоговый статус заказа. Модель прогнозирует успешный исход заказа, созданного в целевом окне, а не обязательно завершение платежа до конца этого окна.

## 5. Time-Based Validation

Чтобы избежать некорректного использования будущих данных, разделение осуществляется по времени, а не случайным образом.

### Обучение и финальное тестирование

| Часть данных | Период |
|---|---|
| Training | Январь — июль 2026 |
| Holdout Test | Август 2026 |

Для подбора параметров использовалась расширяющаяся временная кросс-валидация — **expanding-window cross-validation**.

| Fold | Train | Validation |
|---|---|---|
| 1 | Январь — март | Апрель |
| 2 | Январь — апрель | Май |
| 3 | Январь — май | Июнь |
| 4 | Январь — июнь | Июль |

Такой подход ближе к реальному сценарию: обучение на прошлых данных и получение прогнозов для следующего периода.

Августовский набор не включался в обучение и подбор гиперпараметров.

## 6. Models

### Baseline — Logistic Regression

Для первоначального сравнения использовалась логистическая регрессия с предварительной обработкой признаков:

- заполнение пропущенных числовых значений медианой;
- масштабирование числовых признаков через StandardScaler;
- One-Hot Encoding для категориального признака `country`.

Также рассматривался DummyClassifier, предсказывающий наиболее частый класс.

Воспроизводимое сравнение на том же августовском holdout:

```bash
python src/evaluate_baselines.py
```

Для DummyClassifier выводятся ROC-AUC и AP. Его одинаковые оценки не позволяют ранжировать пользователей, поэтому Precision@100 и Lift@100 не интерпретируются. Итоги последней проверки моделей записаны в `models/evaluation.json`.

### Final Model — CatBoost

В качестве финальной модели выбран CatBoostClassifier.

CatBoost позволяет работать с категориальными признаками и моделировать нелинейные зависимости между характеристиками пользовательской активности.

Конфигурация финальной модели:

```json
{
  "depth": 3,
  "learning_rate": 0.015254729458052608
}
```

Дополнительные настройки:

```python
iterations = 400
loss_function = "Logloss"
random_seed = 42
cat_features = ["country"]
```

Для подбора гиперпараметров CatBoost использовалась Optuna с 10 испытаниями и расширяющейся временной кросс-валидацией на четырёх фолдах.

После исправления доступности длительности сессий на момент прогноза датасет пересобран, подбор проведён повторно, а финальная модель переобучена. Данные августовского holdout в подборе не использовались.

**Результаты:**
- Best CV Average Precision: **0.09672**
- Best depth: **3**
- Best learning_rate: **0.015254729458052608**

Финальная модель обучена на данных за январь–июль 2026 года и оценена на отложенном августовском наборе.

## 7. Evaluation Metrics

Для оценки модели используются:

- **ROC-AUC** — способность ранжировать положительные и отрицательные объекты;
- **Average Precision (AP)** — качество ранжирования положительного класса по precision-recall;
- **Precision@100** — доля успешных покупателей среди 100 пользователей с наибольшей прогнозируемой вероятностью;
- **Lift@100** — отношение Precision@100 к общей доле положительного класса.

### Final Results — August 2026

| Metric | Result |
|---|---:|
| ROC-AUC | **0.6452** |
| Average Precision | **0.0767** |
| Precision@100 | **0.1000** |
| Lift@100 | **2.8090** |

В августовском наборе:

- 2 500 пользователей;
- 89 положительных примеров;
- доля положительного класса — 3,56%.

Среди 100 пользователей с наивысшими прогнозами 10 действительно имели успешную покупку.

Таким образом, Precision@100 составляет 10%, что примерно в **2,81 раза выше случайного базового уровня**.

Метрики получены на синтетических данных. Они показывают работоспособность пайплайна, но не гарантируют аналогичное качество на реальных покупателях.

### Сравнение моделей на том же holdout

| Модель | ROC-AUC | Average Precision | Precision@100 |
|---|---:|---:|---:|
| DummyClassifier | 0.5000 | 0.0356 | — |
| Logistic Regression | 0.6273 | 0.0851 | 0.1100 |
| CatBoost | 0.6452 | 0.0767 | 0.1000 |

На этом синтетическом holdout наибольший AP у Logistic Regression. Параметры моделей по результатам holdout не подбирались. Числа и параметры эксперимента сохранены в `models/evaluation.json`.

## 9. Installation and Setup

### Requirements

Необходимы:

- Python с совместимыми версиями зависимостей из `requirements.txt`;
- PostgreSQL;
- Git (для работы с репозиторием).

### 1. Clone Repository

```bash
git clone https://github.com/brxkennai/ML_Shop.git
cd ML_Shop
```

### 2. Create Virtual Environment

```bash
python -m venv .venv
```

Для Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

### 3. Install Dependencies

```bash
python -m pip install -r requirements.txt
```

### 4. Configure PostgreSQL

Создайте базу данных `ml_shop` и выполните SQL-скрипт:

```text
sql/01_create_tables.sql
```

Скопируйте `.env.example` в `.env` и укажите параметры подключения:

```dotenv
PGHOST=localhost
PGPORT=5432
PGDATABASE=ml_shop
PGUSER=postgres
PGPASSWORD=your_password_here
```

Не публикуйте реальный `.env` в GitHub.

### 5. Generate and Import Data

Пример генерации синтетических данных:

```bash
python src/generate_data.py --users 2500 --seed 42 --out data
```

Затем импортируйте CSV в предварительно созданные пустые таблицы:

```bash
python src/import_to_postgres.py
```

Повторный импорт в уже заполненные таблицы может привести к конфликтам первичных ключей или дублированию данных.

### 6. Build ML Dataset

```bash
python src/build_dataset.py
```

Результат:

```text
data/processed/dataset.csv
```

Датасет формируется для восьми временных срезов с января по август 2026 года.

### 7. Train Final Model

```bash
python src/train.py
```

Модель сохраняется по пути:

```text
models/catboost_final.cbm
```

### 8. Evaluate Model

```bash
python src/evaluate_model.py
```

Скрипт оценивает модель на августовском наборе и выводит ROC-AUC, AP, Precision@100 и Lift@100.

### 9. Generate Predictions

```bash
python src/predict.py
```

Скрипт загружает сохранённую модель и формирует прогнозы для пользователей августовского среза.

Результат:

```text
data/predictions/august_predictions.csv
```

Выходной файл содержит:

```text
user_id
snapshot_date
purchase_probability
```

Пользователи сортируются по убыванию прогнозируемой вероятности успешной покупки.

Это пакетный исторический прогноз. Для использования в реальном времени потребуется отдельное построение актуальных признаков.

## 10. Hyperparameter Tuning

Подбор параметров вынесен в отдельный модуль `src/tune.py`.

Для просмотра сохранённых параметров:

```bash
python src/tune.py
```

Для нового запуска Optuna:

```bash
python src/tune.py --run --trials 10
```

**Внимание:** повторный подбор обучает CatBoost на нескольких временных фолдах и может потребовать значительного времени.

Обычный запуск `tune.py` не запускает оптимизацию.

После успешного подбора `config/best_params.json` автоматически заменяется найденными параметрами. Затем запустите `python src/train.py`, оценку и прогнозы, чтобы обновить модель и результаты. Если подбор завершается ошибкой, предыдущий файл параметров сохраняется.

## 11. Automated Testing

В проекте используются автоматические тесты `pytest`.

Проверяются:

- расчёт ML-метрик;
- обработка некорректных параметров;
- наличие обязательных столбцов датасета;
- отсутствие дубликатов пользователей внутри одного временного среза;
- бинарность целевой переменной;
- корректность числовых счётчиков;
- временные границы признаков;
- временные границы целевой переменной;
- независимость исторических признаков от будущих событий;
- учёт только `completed`-заказов в положительном классе.

Запуск:

```bash
python -m pytest tests/ -v
```

В текущем наборе предусмотрено **22 проверки**, включая параметризованные случаи. Дополнительно проверяются доступность итоговой длительности сессий на момент прогноза, сохранение результатов подбора параметров и отсутствие запуска пайплайна при импорте модулей.

Интеграционные SQL-тесты используют временные таблицы PostgreSQL и требуют доступного подключения к базе данных.

## 12. Limitations and Future Improvements

Проект имеет ряд ограничений:

1. **Синтетические данные.** Распределения пользовательского поведения могут существенно отличаться от реальных.
2. **Итоговый статус заказа.** Статус `completed` не имеет отдельной временной истории; для реальной системы необходимо учитывать момент его появления и доступность целевых меток.
3. **Ограниченный набор признаков.** В текущей версии не используются денежные агрегаты, история возвратов, характеристики товаров и многие другие потенциально полезные признаки.
4. **Временные срезы.** Один пользователь присутствует в нескольких месяцах; для честной оценки необходимо сохранять временной порядок и учитывать пересечение исторических окон.
5. **Подбор параметров.** Выполнено 10 испытаний на четырёх временных фолдах; это ограниченный поиск, который не гарантирует глобально оптимальных параметров.
6. **Исторический режим прогнозирования.** `predict.py` работает с подготовленным августовским срезом, а не с потоковыми данными реального интернет-магазина.
7. **Проверка качества данных.** Необходим дополнительный контроль полноты событий, корректности дат регистрации и статусов заказов перед реальным внедрением.

Возможные дальнейшие улучшения:

- Добавление RFM-признаков и других пользовательских агрегатов.
- Интерпретация модели через SHAP.
- Версионирование данных и экспериментов.
- REST API через FastAPI.
- Контейнеризация через Docker.
- Мониторинг качества прогнозов и дрейфа данных.
